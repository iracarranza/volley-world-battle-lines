# Behavioural Divergence Register (BDR)

Migration stage MS-01. The register lists behaviour that the code shows today and that nobody has judged. It changes no behaviour. Rule for every migration stage: **reproduce, do not fix**. A refactor that makes any entry differ is a gameplay change (constitution class X5), not a refactor, and stops.

Each entry has a citation (file and symbol in this repository; line numbers drift, so symbols are the anchor), the actors affected, a status, a pin test, and a gate. Status values: `CURRENT-reproduced`, `CHANGED` (a CHANGE stage landed, pin and golden updated), `GATED`, `DESIGNER-APPROVED-AS-IS`. Gates G-nn are decided provisionally (designer-delegated, revocable, see the study's `gate-decisions-provisional.md`). An entry does not decide its gate. Pin tests exist since MS-05: one pin function per scenario in `tests/support/bdr_pins.gd` (asserting the CURRENT behaviour recorded in the entry, quirks included), run by the three catalogue shards, with the scenario traces checked in as golden files under `tests/golden/` (regeneration procedure in `tests/golden/README.md`). `tests/characterization_coverage_test.gd` lints that every entry has a pin function and that the register names it.

Evidence tags: SRC (read in source), VER (executed by the study probes on 2026-11-16, `16-probe-and-baseline-results.md`), INF (inferred).

## Maintenance rules

1. An entry needs a citation and a pin test (a pin function in `bdr_pins.gd` plus its scenario). No entry without both.
2. An entry may be closed only by a gate answer, a behaviour-change decision record and a status change, never as a side effect of a stage.
3. Entries do not decide gates. `DESIGNER-APPROVED-AS-IS` is a designer act.
